# Резервні копії

Коротко: **щоночі GitHub Actions знімає SQL-дамп бази D1 `nasvitlo` і
зберігає його 90 днів як артефакт — поза Cloudflare.** Поки власник не додав
два секрети, workflow просто пише «пропущено» і завершується зеленим.

Файл: `.github/workflows/d1-backup.yml`.

## Що копіюється

| Що | Де живе | Чим захищене |
|---|---|---|
| **Контент адмінки EmDash** — огляди, справи, тексти сторінок, чернетки, ревізії, користувачі адмінки, налаштування | D1 `nasvitlo` (id `bbde7a56-829d-49b3-b898-eede9a347fa3`) | нічний дамп (цей документ) + D1 Time Travel (30 днів) |
| **Код і контент у файлах** (`src/content/*.ts`, стилі, компоненти) | репозиторій GitHub | історія git |
| **Фото команди й логотипи** | файли в `public/` (`/team/*`, `/logos/*`) | історія git |
| **Медіатека EmDash** | R2 `nasvitlo-media` | *сьогодні не використовується* — див. нижче |

**R2 сьогодні порожній за змістом.** Бакет підключено (без нього Worker не
деплоїться), але фото й логотипи — це рядки-шляхи на файли в `public/`, а не
медіа EmDash (docs/CLOUDFLARE.md, «Відомі обмеження»). Коли їх переведуть на
поля `image` із завантаженням у R2, бекап знадобиться і для R2 — дамп D1
містить лише посилання на об'єкти, а не самі файли. Тоді цей документ треба
доповнити (наприклад, `rclone sync` з R2 у сховище поза Cloudflare).

**Резервні копії в самій адмінці EmDash** («Щоденні автоматичні резервні
копії» у R2) — корисне доповнення, але вони в тому самому акаунті
Cloudflare, що й база. Від втрати акаунта чи помилкового видалення захищає
лише копія поза ним — ця.

**Пошуковий індекс.** EmDash тримає повнотекстовий пошук у віртуальних
таблицях FTS5 (`_emdash_fts_<колекція>`), а D1 не вміє експортувати
віртуальні таблиці. Якщо повний експорт на них упаде, workflow сам
перемкнеться на експорт усіх звичайних таблиць поіменно і прибере з дампу
тригери, що пишуть в індекс (інакше відновлення впало б на першому ж
`INSERT`). Режим видно в підсумку запуску: `full` або `tables-without-fts`.
Індекс відтворюваний з контенту — EmDash перебудовує відсутню FTS-таблицю
сам (`verifyAndRepairAll` під час пошуку); вручну — адмінка, пошук, або
`POST /_emdash/api/search/rebuild` з правом `search:manage`.

## Увімкнути (разова дія власника)

### 1. Токен Cloudflare з мінімальними правами

1. <https://dash.cloudflare.com/profile/api-tokens> → **Create Token** →
   **Create Custom Token** → *Get started*.
2. **Token name:** `nasvitlo d1 backup (GitHub Actions)`.
3. **Permissions:** один рядок — **Account** · **D1** · **Edit**.
   Нічого більше: ні Workers, ні інших сервісів.
4. **Account Resources:** *Include* → `Vm@bot-partners.com's Account`.
5. (За бажання) **Client IP Address Filtering** не ставити — IP раннерів
   GitHub змінюються. **TTL** можна лишити порожнім або поставити рік і
   записати собі нагадування.
6. **Continue to summary** → **Create Token** → скопіювати токен (показують
   один раз).

> **Чому Edit, а не Read.** `wrangler d1 export` створює на боці Cloudflare
> завдання експорту, і з правом *Read* Cloudflare відповідає
> `Authentication error [code: 10000]` — перевірено першим запуском
> 26 вересня 2026. Edit ширше, ніж хотілося б: токен може й змінювати
> базу. Тож тримайте його тільки в секретах GitHub і більше ніде.

### 2. Секрети в GitHub

Репозиторій `bnp-team/zivik-platform` → **Settings** → **Secrets and
variables** → **Actions** → **New repository secret**, двічі:

| Name | Secret |
|---|---|
| `CLOUDFLARE_API_TOKEN` | токен із кроку 1 |
| `CLOUDFLARE_ACCOUNT_ID` | `55d2d3b8fd8d4d615a297eb49f5622c9` |

### 3. Перевірити

**Actions** → **d1-backup** → **Run workflow** → *main* → **Run workflow**.
Через хвилину-дві в запуску має з'явитися таблиця «D1 backup» (розмір, число
`INSERT`, SHA-256) і внизу, в **Artifacts**, файл
`nasvitlo-d1-<дата>.sql.gz`.

> Scheduled-запуски GitHub виконує лише з гілки за замовчуванням (`main`):
> доки workflow не злитий у `main`, нічних копій не буде — тільки ручні.
> А ще GitHub вимикає `schedule` у репозиторії, де 60 днів не було
> активності, — тоді на сторінці workflow з'явиться кнопка **Enable
> workflow**.

Токен у лог не потрапляє: GitHub маскує секрети, у лог нічого з них не
виводиться, а сам токен доступний лише кроку експорту — `npm ci` його не
бачить.

## Відновлення

Правило одне: **ніколи не відновлювати поверх робочої бази.** Спершу — у
нову, перевірити, потім перемкнути.

### Варіант А — Time Travel (останні 30 днів, найшвидше)

D1 сам пам'ятає кожну хвилину за останні 30 днів (Workers Free — 7 днів).
Це відкат **тієї самої** бази, тож спершу зафіксуйте поточний стан:

```sh
npx wrangler d1 time-travel info nasvitlo                       # поточна закладка — ЗАПИСАТИ
npx wrangler d1 time-travel restore nasvitlo --timestamp=2026-09-20T12:00:00Z
```

`restore` виведе закладку стану *до* відкату — з нею можна повернутися
назад (`--bookmark=<закладка>`). Після відкату — нова збірка сайту
(Workers & Pages → nasvitlo → Deployments → Retry або будь-яка публікація
в адмінці), щоб сторінки перезібралися з відновленого контенту.

### Варіант Б — з нічного дампу (старше 30 днів або база зникла)

1. **Завантажити дамп:** GitHub → Actions → d1-backup → потрібний запуск →
   Artifacts → `nasvitlo-d1-….sql.gz` (приходить zip-архівом; усередині
   `.sql.gz`).

   ```sh
   unzip nasvitlo-d1-*.zip
   sha256sum nasvitlo-d1-*.sql.gz   # має збігтися з SHA-256 у підсумку запуску
   gunzip nasvitlo-d1-*.sql.gz
   ```
2. **Створити НОВУ базу** (стару не чіпати):

   ```sh
   npx wrangler d1 create nasvitlo-restore-2026-09-26 --location=eeur
   ```
3. **Залити дамп у нову базу.** Спершу розрізати задовгі команди: D1 не
   приймає команду понад 100 КБ, а рядки оглядів і їхніх ревізій більші, і
   без цього імпорт падає з `D1_RESET_DO`. Той самий скрипт ставить усі
   `CREATE TABLE` перед даними, а індекси й тригери після них: дамп у режимі
   `tables-without-fts` іде за абеткою, і D1, що перевіряє зовнішні ключі,
   інакше зупиняється на «no such table: main.media_folders». У бекапах до
   7 жовтня 2026 у цьому режимі індексів і тригерів немає взагалі — їх тоді
   доведеться взяти зі схеми живої бази (`scripts/cf/move-account.sh`, крок 1).

   ```sh
   python3 scripts/cf/split-long-inserts.py nasvitlo-d1-….sql nasvitlo-d1-….sql
   npx wrangler d1 execute nasvitlo-restore-2026-09-26 --remote --file=nasvitlo-d1-….sql
   ```
4. **Перевірити** — порахувати записи й порівняти з очікуваним (і зі старою
   базою, якщо вона жива):

   ```sh
   npx wrangler d1 execute nasvitlo-restore-2026-09-26 --remote \
     --command "SELECT name FROM sqlite_master WHERE type='table' ORDER BY name"
   npx wrangler d1 execute nasvitlo-restore-2026-09-26 --remote \
     --command "SELECT COUNT(*) FROM ec_summaries"   # або інша колекція
   ```
5. **Перемкнути binding:** у `wrangler.jsonc` в `d1_databases` замінити
   `database_name` і `database_id` на нові (id друкує `d1 create`),
   закомітити, дочекатися збірки й деплою. Binding лишається `DB` —
   код не змінюється.
6. **Після перемикання:** відкрити `/_emdash/admin`, увійти, відкрити
   кілька записів, зробити пошук в адмінці (перебудує індекс, якщо дамп був
   у режимі `tables-without-fts`), опублікувати одну дрібну правку — вона
   має дійти до сайту.
7. Стару базу не видаляти щонайменше місяць.

## Навчальне відновлення (раз на квартал)

Бекап, який ніхто не пробував відновити, — це надія, а не бекап.
Чекліст (~20 хвилин), результат записати в кінці цього файлу:

- [ ] Actions → d1-backup: останній нічний запуск зелений, не старший за добу.
- [ ] Режим у підсумку — `full` чи `tables-without-fts`? Якщо змінився без
      причини — розібратися.
- [ ] Завантажити артефакт, звірити SHA-256, розпакувати.
- [ ] `wrangler d1 create nasvitlo-drill-<дата>`.
- [ ] `wrangler d1 execute nasvitlo-drill-<дата> --remote --file=…` — без помилок.
- [ ] Кількість рядків у 2–3 основних таблицях збігається з робочою базою
      (з поправкою на правки після нічного запуску).
- [ ] Відкрити в дампі один свіжий огляд і переконатися, що текст цілий
      (кирилиця, лапки «», апострофи).
- [ ] `wrangler d1 time-travel info nasvitlo` — Time Travel відповідає.
- [ ] Видалити навчальну базу: `wrangler d1 delete nasvitlo-drill-<дата>`.
- [ ] Дописати рядок у журнал нижче.
